Thought for 4s

「先只給『每週預訂台數 + 機台資料』」這個做法,好處主要來自於它剛好卡在『現場能做到』與『系統能可靠算出』的交集點,不會做超過現況能支撐的事。具體好處如下:
1. 不需要假的精確度,反而更貼近實際運作

    現場是「隨機從箱子拿」,如果系統硬要排「哪一台在哪一週換」,那份排程從第一天就是假的——現場不會照著做,你也沒辦法追蹤是否真的照排程執行。
    只給「台數 + 建議優先清單」,不強制對應到具體某一台實體設備,系統輸出的東西剛好等於現場真正能參考、真正能用的資訊,不會產生「系統說的跟現場做的對不起來」的落差感。

2. 現場人力/物流可以提前準備,不用臨時應變

    知道「下週要換 87 台」,現場就能提前:
        排定要派多少人力去換機
        確認箱子裡庫存夠不夠(不夠的話提前催外部維修回補)
        安排運送/搬運排程
    這是目前唯一真正需要提前知道的資訊——「量」而不是「哪一台」,因為「哪一台」在你的情境下本來就是當下才決定的。

3. 把「預測」跟「執行」拆開,兩邊各自可以獨立進化

    現階段:預測(三層退回機制算出的到期日/風險)→ 產生「建議清單」;執行(現場隨機拿取)→ 是另一件事,兩者暫時不用綁死。
    好處是:未來如果你想加入「庫存平衡」「入庫追蹤」這些更複雜的功能,不需要動到現有的預測演算法,只需要在「執行端」多加一層邏輯(例如比對箱內庫存 vs 建議台數),風險小、改動範圍可控。

4. 提供「優先權排序」給現場,而不是替現場做決定

    明細清單依「已逾期優先、到期日越近越優先」排序,現場人員可以照著清單由上往下挑,盡量把風險最高的位置先處理掉——但仍保有彈性,不會被綁死。
    也就是說,系統負責告訴現場「先做哪些、大概要做多少台」,現場負責決定「用哪一台實體設備去換」——這個分工剛好對應你們目前的組織現況(系統沒有能力管到箱子裡的實體庫存細節)。

5. 可以直接拿來做管理報表 / 採購決策依據

    每週台數趨勢一拉出來,主管可以看到:
        未來幾週的維運負荷是否會超過每週產能上限(1000 台)→ 提前調配人力或调整標準週期
        某些分類的機台是否密集到期 → 提前評估是否要加購備用機、加快維修回補速度
    這些都是「台數」層級就能做的管理決策,不需要細到「機台編號」才能用。

6. 避免過度工程化,先驗證核心價值

    你現在最需要驗證的是:「三層退回機制算出來的週期基準,準不準、有沒有實際參考價值」。
    如果第一版就把「箱子庫存管理」「入庫配對」全部做進去,一旦核心的週期預測邏輯需要調整(例如優先序 2 要不要加樣本數門檻),牽動的範圍會變很大,除錯也更困難。
    先把「台數 + 建議清單」這個最小可用版本跑起來,讓現場實際使用一段時間、回饋準確度後,再決定要不要往「庫存平衡」方向擴充,是風險最低的做法。

一句話總結:因為現場是「隨機取放 + 動態入庫」,系統目前沒有能力(也不需要)去追蹤箱子裡每一台實體設備的即時狀態,所以先把系統的輸出降階到「量」的層級——這剛好是現場真正能用、你也真正能可靠算出來的資訊,同時保留未來擴充「庫存平衡」功能的空間,不會因為現在做得太複雜而綁死自己。

採三層退回機制，資料越具體優先權越高：
優先序	判斷條件	標準週期來源
1	該機台本身歷史換機 ≥ 2 次	用「該機台自己」歷次換機的平均間隔天數
2	機台歷史不足，但同分類有其他機台有足夠樣本	用「同分類機台」的平均換機週期

這一步就是「平均分配換機時機標準」的核心：讓每台機台都有一個可依循的週期基準，而不是憑經驗猜測。

請幫我說明程式分別對應 1 2 3 的代碼說明


優先序 1:機台自身歷史換機 ≥ 2 次

位置:第 1129–1141 行,terminalAvgInterval

javascript
const terminalAvgInterval = computed(()=>{
  const map = {};
  dataset.terminals.forEach(t=>{
    const hist = (eventsByTerminal.value[t.terminalId]||[]).slice().sort((a,b)=>a.date.localeCompare(b.date));
    if(hist.length>=2){
      let sum=0;
      for(let i=1;i<hist.length;i++) sum += daysBetween(hist[i-1].date, hist[i].date);
      map[t.terminalId] = sum/(hist.length-1);
    }
  });
  return map;
});
針對每一台機台,把該機台自己的歷史換機事件依日期排序。
hist.length>=2 正是「歷史換機 ≥ 2 次」的判斷條件 —— 因為要算「間隔天數」至少需要兩個時間點才有一個區間。
用 daysBetween 逐一計算相鄰兩次換機的天數差,加總後除以區間數 (hist.length-1),得到該機台自己的平均換機間隔。
沒有樣本(換機 < 2 次)的機台,不會被塞進 map,所以之後查 terminalAvgInterval.value[t.terminalId] 會是 undefined(即 own==null),自然會退回下一層。
優先序 2:同分類其他機台有足夠樣本

位置:第 1143–1156 行,categoryAvgInterval

javascript
const categoryAvgInterval = computed(()=>{
  const groups = {};
  dataset.terminals.forEach(t=>{
    const v = terminalAvgInterval.value[t.terminalId];
    if(v!=null) (groups[t.category]=groups[t.category]||[]).push(v);
  });
  const map = {};
  Object.keys(groups).forEach(cat=>{
    const arr = groups[cat];
    map[cat] = arr.reduce((a,b)=>a+b,0)/arr.length;
  });
  return map;
});
這裡故意不是拿分類底下所有機台的原始換機事件重算,而是直接引用上一層算好的 terminalAvgInterval。
只收集「已經有自身樣本」的機台(v!=null)的平均值,放進同分類的陣列 groups[cat]。
再對這個陣列取平均,得到「這個分類、依有樣本機台推算出的標準週期」。
這樣做的好處:分類平均只由「真正發生過 ≥2 次換機的機台」貢獻,不會被還沒有歷史資料的機台稀釋或污染。
優先序 3:全站平均(分類樣本也不足時的最終退回)

位置:第 1158–1163 行,globalAvgInterval

javascript
const globalAvgInterval = computed(()=>{
  const vals = Object.values(terminalAvgInterval.value);
  if(!vals.length) return 365;
  return vals.reduce((a,b)=>a+b,0)/vals.length;
});
把全站所有「有自身樣本」機台的平均間隔,不分分類全部攤平取平均。
if(!vals.length) return 365 是保底:萬一全站連一台機台都沒有 ≥2 次換機紀錄(冷啟動情境),就先給一個預設 365 天的週期,避免算出 NaN 或除以 0。

位置:第 1187–1203 行,forecastList(這才是真正「依序判斷、選一個用」的地方)

javascript
const forecastList = computed(()=>{
